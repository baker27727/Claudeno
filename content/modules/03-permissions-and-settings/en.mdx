# Permissions & Settings

`settings.json` controls what Claude Code is *allowed to do*. It exists at several
scopes:

| Scope | Path | Shared with team? |
|---|---|---|
| Project | `.claude/settings.json` | Yes (committed) |
| Local | `.claude/settings.local.json` | No (gitignored, personal) |
| User | `~/.claude/settings.json` | No, applies to all your projects |

## Permissions: allow and deny

```bash
cat .claude/settings.json
```

```json
{
  "permissions": {
    "allow": ["Bash(npm run test *)"],
    "deny": ["Read(./.env)"]
  }
}
```

Patterns use the tool name plus an argument pattern in parentheses, with `*`
wildcards. **`deny` always wins** when a pattern matches both lists.

<Callout type="tip" title="Tip">
  Start narrow. Allow-list a handful of read-only or low-risk commands first
  (`Bash(npm run test *)`, `Bash(git status)`), then widen the list as you see what
  Claude actually needs — instead of allowing broad patterns like `Bash(*)` up front.
</Callout>

You can review and edit these rules without hand-editing JSON: run `/permissions`
inside a session to open an interactive dialog for allow, ask, and deny rules by
scope.

## Plan mode

```bash
claude --permission-mode plan
```

Starts a session where Claude proposes its plan before making any changes —
handy for reviewing risky work before it happens.

## settings.json vs. CLAUDE.md

`settings.json` configures *behavior* (permissions, hooks, model). `CLAUDE.md` gives
Claude *context* — project conventions, architecture notes, style guides — that it
reads at the start of every session.

## Key takeaways

- `.claude/settings.json` is the shared, committed scope; `.local.json` is personal.
- `deny` beats `allow` whenever a pattern matches both.
- `/permissions` gives you an interactive dialog instead of hand-editing JSON.
- `settings.json` controls what Claude can *do*; `CLAUDE.md` tells it what to *know*.

## What's new in v2.1.204

**What's new (2.1.204):** Fixed a bug affecting headless sessions where hook events (e.g. `SessionStart` hooks) did not stream properly, which could cause remote workers to be idle-reaped while a hook was still running. No settings changes are required to benefit from this fix.

## What's new in v2.1.205

Starting in version 2.1.200, the "default" permission mode has been renamed to "Manual" across the CLI and settings. You can use both --permission-mode manual and "defaultMode": "manual" in configuration. A grey ⏸ badge now shows in the footer when in manual permission mode (added in 2.1.203), making the active mode always visible.

## What's new in v2.1.207

Auto mode is now available by default on Bedrock, Vertex AI, and Foundry without requiring the `CLAUDE_CODE_ENABLE_AUTO_MODE` opt-in. You can disable it using the `disableAutoMode` setting. Note that auto mode no longer reads from `.claude/settings.local.json` (repo-resident); configure it in `~/.claude/settings.json` instead. Plugin option values (`pluginConfigs`) are also no longer read from project-level settings—use user settings, `--settings`, or managed settings.

## What's new in v2.1.209

New accessibility option: screen reader mode provides opt-in plain-text rendering for screen reader users. Enable it by running `claude --ax-screen-reader`, setting `CLAUDE_AX_SCREEN_READER=1` in your environment, or adding `"axScreenReader": true` to your settings.

New setting `vimInsertModeRemaps`: configure two-key insert-mode sequences like `jj` to map to Escape in vim mode.

New environment variable `CLAUDE_CODE_PROCESS_WRAPPER`: corporate launchers can now wrap every Claude Code self-spawn by setting this to a required wrapper executable. The agent view and background service honor this wrapper.

## What's new in v2.1.210

Claude Code 2.1.210 adds startup warnings for `Write(path)`, `NotebookEdit(path)`, and `Glob(path)` permission rules — the recommended approach is to use `Edit(path)` or `Read(path)` instead for more precise access control.

## What's new in v2.1.211

Permission rules have been improved: when you grant "always allow" permissions within a git worktree, they now save at the repository root and persist across sessions and worktrees. Additionally, permission previews relayed to chat channels now neutralize bidirectional-override, zero-width, and look-alike quote characters to prevent tool inputs from visually altering approval messages.

## What's new in v2.1.214

Permission checks have been improved in Claude Code 2.1.214. Single-segment `dir/**` allow rules now match only `<cwd>/dir` instead of `dir/` anywhere in the tree (write `**/dir/**` for any-depth matching). Additionally, permission prompts now appear for `docker` commands carrying daemon-redirect flags (`--url`, `--connection`, `--identity`) that previously ran without approval.

## What's new in v2.1.216

Claude Code 2.1.216 introduces the `sandbox.filesystem.disabled` setting, which lets you skip filesystem isolation while maintaining network egress control. This is useful in sandboxed environments where you need fine-grained control over isolation boundaries.

## What's new in v2.1.217

Corporate mTLS, TLS verification, OAuth scope, and proxy settings are now properly honored in Claude Desktop sessions, fixing a previous issue where these security and connectivity settings were ignored. Screen reader mode's startup announcement no longer gets cut off by the first prompt render.

## What's new in v2.1.218

Added `sandbox.filesystem.disabled` setting to skip filesystem isolation while keeping network egress control. Screen reader mode (`--ax-screen-reader`) now includes screen-reader announcements for word and line deletions. The `emojiCompletionEnabled` setting controls emoji shortcode autocomplete (e.g., type `:heart:` for ❤️). Boolean values in skill and plugin frontmatter now accept `yes`/`no`/`on`/`off`/`1`/`0` (case-insensitive) alongside `true`/`false`.

## What's new in v2.1.220

**What's new in 2.1.220:** A new setting `sandbox.network.strictAllowlist` has been added to deny non-allowlisted hosts for sandboxed commands without prompting. The `sandbox.filesystem.disabled` setting (available since 2.1.216) continues to allow skipping filesystem isolation while maintaining network egress control.

## What's new in v2.1.222

**Auto mode safety improvements (2.1.222)**: Messages sent to other agent sessions via `SendMessage` are now evaluated by the permission classifier before dispatch, strengthening isolation between concurrent sessions.
