# Hooks

Hooks are shell commands that run automatically at specific points in Claude Code's
lifecycle — before a tool call, after an edit, when Claude finishes responding, and
more. They give you **deterministic** control: a rule that always fires, instead of
relying on the model to remember to run a formatter or check a policy every time.

## The hooks block

Hooks live under a `hooks` key in a settings file. Each event name is its own key
inside that object, holding an array of matcher groups:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" }
        ]
      }
    ]
  }
}
```

`matcher` narrows which tool calls trigger the hook — here, only `Edit` or `Write`
calls run Prettier. An empty matcher (`""`) fires on every occurrence of the event.
Each hook receives the event data as JSON on stdin and tells Claude Code what to do
next through its exit code: `0` means no objection, `2` blocks the action and sends
your stderr message back to Claude as feedback.

## Common events

| Event | Fires when |
|---|---|
| `SessionStart` | A session begins or resumes |
| `UserPromptSubmit` | You submit a prompt, before Claude processes it |
| `PreToolUse` | Before a tool call executes — can block it |
| `PostToolUse` | After a tool call succeeds |
| `Stop` | When Claude finishes responding |
| `Notification` | When Claude Code sends a notification (e.g. waiting for input) |

## Example: block edits to protected files

A `PreToolUse` hook can stop an edit before it happens. This script checks the
target path against a list of protected patterns and exits with code `2` — the exit
code that blocks the tool call — when it matches:

```shell
#!/bin/bash
# .claude/hooks/protect-files.sh
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

for pattern in ".env" "package-lock.json" ".git/"; do
  if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Blocked: $FILE_PATH matches protected pattern '$pattern'" >&2
    exit 2
  fi
done
exit 0
```

Make it executable, then register it as a `PreToolUse` hook matching `Edit|Write` in
`.claude/settings.json`:

```bash
chmod +x .claude/hooks/protect-files.sh
```

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh" }
        ]
      }
    ]
  }
}
```

<Callout type="tip" title="Test a hook script directly">
  Before registering a hook, pipe sample JSON into it to check the exit code:

  ```bash
  echo '{"tool_input":{"command":"ls"}}' | ./my-hook.sh
  ```
</Callout>

## Verify and debug

```
/hooks
```

`/hooks` opens a read-only browser of every configured hook, grouped by event, with
a count next to each one. To add, modify, or remove a hook, edit the settings JSON
directly (or ask Claude to do it) — the menu itself can't write changes.

<Callout type="mistake" title="Common mistake">
  Matching too broadly. A `PermissionRequest` hook with an empty or `.*` matcher
  auto-approves *every* permission prompt, including file writes and shell commands —
  not just the one you meant to skip. Keep matchers as narrow as the tool name (or
  tool name + `if` pattern) you actually intend to cover.
</Callout>

For deeper debugging, start a session with a known log path and tail it in another
terminal:

```bash
claude --debug-file /tmp/claude.log
```

## Summary

- Hooks run shell commands deterministically at lifecycle events — they don't depend
  on the model choosing to act.
- The shape is always `hooks.<EventName>[].{matcher, hooks: [{type: "command",
  command}]}`.
- Exit code `0` = no objection, exit code `2` = block and feed your stderr message
  back to Claude as feedback.
- `/hooks` is read-only for browsing; edit the settings file to change hooks.
- Keep matchers narrow, especially for auto-approving `PermissionRequest` hooks.

## Related skills

Hooks enforce; skills instruct. If something must *never* be forgotten, use a hook — if Claude should know *how* to do something, use a skill. See [Skills & SKILL.md](/en/learn/skills/) and the [skills catalog](/en/skills/).

## What's new in v2.1.207

Plugin hooks now reject `${user_config.*}` in shell-form commands as a shell-injection security fix. Use exec form (`args` array) or the `$CLAUDE_PLUGIN_OPTION_<KEY>` environment variable instead. Monitors and headersHelper should read config values inside the script rather than via command interpolation.

## What's new in v2.1.211

Auto mode behavior has been refined: a PreToolUse hook's `ask` decision now floors the decision at a prompt instead of being overridden by auto mode for unsandboxed Bash, ensuring hook developers have explicit control over approval behavior.

## What's new in v2.1.214

SessionStart hooks now report source `"fork"` when a session begins as a fork instead of `"resume"`. Additionally, single-segment `dir/**` hook `if:` conditions have changed to match only `<cwd>/dir`; use `**/dir/**` for any-depth matching. Note that `deny`/`ask` permission rules retain their original any-depth behavior.

## What's new in v2.1.229

**New in 2.1.229:** Server-supplied Claude Code hooks are now supported in self-hosted runner sessions, providing the same hook functionality available in managed environments.
